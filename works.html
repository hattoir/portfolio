【システム概要】

床の紙くずを見つけ、接近・把持・投下・巡回復帰までを行う清掃ロボットを開発しています。私が取り組んでいるのは、車体とアームの機構設計、ROS 2による制御、画像・深度認識の接続です。各機能を個別に動かすだけでなく、届く位置へ停車することやセンサの死角まで含めて、一連の作業を成立させることを課題にしています。

まずROS 2とGazeboで統合し、機構と制御の問題を実機製作前に洗い出す方針です。2026年7月の開発記録には、無介入20分のシミュレーション統合試験に合格した節目があります。その後は実機のアーム・車体・駆動方式に合わせた改修を進めています。これは当時のモデルと条件での結果であり、現在の実機の連続稼働実績とは分けて扱っています。

実機化では寸法だけでなく、摩擦、駆動系、センサ誤差、通信遅延を確認する必要があります。移植しやすい構成を目指しつつ、単体試験から統合試験へ段階を踏み、モデルと実測の差を詰めています。

【ハードウェア設計における課題と工夫】

設計モデルで先に確認することで、必要トルク、到達範囲、センサの干渉を検討できます。以下の数値は開発時のモデル・計算条件に依存し、実機の性能保証値ではありません。

1. トルク計算から機構と動作を見直す

課題： CADモデルの質量・重心に基づく重力トルク計算では、腕を水平にした姿勢で肩関節（J2）に 1.32 N·m が必要という見積もりになりました。使用サーボのストールトルク1.9 N·mに対して約 70%です。ストールトルクは連続運転できるトルクではないため、この比率だけで成立とは判断できません。把持姿勢だけでなく、動作途中の負荷も検討対象にしました。
工夫： 肘を先に畳んでから伸ばす軌道、先端側の軽量化、カウンターバランスを比較する方針です。制御だけで解決しようとせず、機構と動作の両側から負荷を下げ、実機では電流・温度・保持性能を確認します。

2. 到達範囲から停止位置を設計する

課題： 逆運動学の解を格子状に調べ、正面の床面へ届きにくい領域を確認しました。開発モデルでは横方向のずれが4cm以内の領域に制約があり、関節可動域を考慮すると、対象に正対して止まる方法では把持姿勢を作れませんでした。
工夫： 対象が斜め前に来るよう停止位置をオフセットする接近方法へ変更しました。移動とアームを別々に最適化せず、把持できる姿勢から台車の停車位置を決める設計へ見直しました。

3. センサの死角を機構配置から解消する

課題： シミュレーションで走行させたところ、ロボットが 1mm も前進しない現象が発生しました。原因を追跡すると、LiDAR のスキャン面（床上 210mm）を カメラ本体が横切っており、自分自身を至近距離の障害物として検出し続けて速度が制限されていました。
工夫： カメラマストを 25mm 下げて天端とスキャン面の間に 10.3mm のクリアランスを確保し、CAD の干渉解析でスキャン面を横切る構造物がゼロであることを確認しました。残るアームの映り込みについては、遮蔽角を幾何計算（幅 11.9°）してソフト側でその角度セクターのみを除去しています。

4. メカナム輪の運動学 — 実効モーメントアームの取り違えを防止

課題： モータードライバの都合で4輪独立駆動から左右ペア駆動（差動2輪）へ変更した際、旋回の角速度が指令値の 60% しか出ない問題が発生しました。
工夫： メカナムホイールはローラーが 45° に傾いているため、旋回に効く実効モーメントアームは物理トレッドの半分（0.180 m）ではなく lx + ly = 0.300 m になります。この幾何を計算で確かめ、制御パラメータを実効値へ修正することでシミュレーションで指令と移動量の整合を確認しました。実機では滑りや負荷による差を別途測定します。あわせて、実機のマイコン側ファームウェアと最大角速度の見積もり（2.5 → 1.5 rad/s）も同じ根拠で修正しています。

【検証で得た学び / 次の課題】

本プロジェクトで最も多くの時間を費やしたのは、機能の実装そのものではなく「本当に動いているかを確かめる方法」の確立でした。

1. ログを成果の証拠にしてしまった反省 — 物理照合による検証体制の確立

反省点： 開発中盤、ログに「回収完了」と表示されたことをもって完成と判断しました。しかし念のためシミュレータに物体の座標を直接問い合わせたところ、対象は初期位置から 3.5mm しか動いていませんでした。ログは「そう表示するコードが実行された」ことしか証明しないという当たり前の事実を、身をもって理解した出来事でした。
Next Action： 以降は判定基準を「物が実際にどこへ移動したか（シミュレータの真値座標）」に統一しました。合格条件も、回収数・投下位置の誤差・接近距離・巡回継続数といったすべて計測可能な数値で定義し直しています。

2. 物理量を計算せずに設定値を書いた反省 — 開ループ試験による診断

反省点： 長期間、原因不明のまま残っていた不具合が2件ありました。1つは肩関節が可動域の端で固着する問題で、原因はモデルに設定したトルク上限が必要値の 45% しかなかったこと。もう1つは、車輪の回転軸の符号がすべて逆になっており、指令とは逆方向に走りながらオドメトリは「正しく進んだ」と報告し続けていたことでした。
Next Action： どちらも「指令を与えて、実際にどう動いたかを真値で測る」開ループ試験で特定できました。以降、駆動系に変更を加えたら必ずこの試験を通すことをルール化しています。実機でも組み立て後に同じ試験（1m 直進・半回転を巻尺で実測）を行う計画です。

3. 評価数値をそのまま信じた反省 — データリークの検査

反省点： ゴミ検出用に学習させた YOLO モデルが mAP50 = 0.99 という高い数値を出しました。しかし学習データは動画から切り出したフレームであり、それをランダムに分割していたため、評価用の画像が学習用とほぼ同じ場面になっていました。
Next Action： 動画1本を丸ごと評価用に取り分ける方式（Leave-One-Video-Out）で測り直したところ、その評価条件では mAP50 = 0.84 でした。良すぎる数値が出たときは、まず評価方法そのものを疑うという習慣がつきました。

4. 実機完成に向けた残課題

実機化は進行中です。過去の開発記録にはミニPC、LiDAR、深度カメラの個別評価がありますが、2026年10月のUbuntu環境整理では製品の再ビルド・Gazebo統合試験・実機試験は再実行していません。今後、次の項目を段階的に確認します。 ・車輪駆動の実機検証（開ループ試験）
・6軸アームの実機制御（ros2_control ハードウェアインターフェース）
・簡略化していた把持を、実際に指で掴む物理把持へ差し替え
・主板・底板のレーザーカット製作と本組み立て 各試験で、条件・実測値・失敗時の挙動を記録します。シミュレーションの成立と実機の成立を分け、再現できる根拠を揃えて次の段階へ進みます。

【ハードウェア設計における課題と工夫】

Fusion 360を用いた実機設計において、画面上のモデリングと現実の物理的な組み上がりのギャップに最も苦心しました。特に、3Dプリンター等で出力した際の「公差の設定」や、各リンク機構が干渉しない適切な「サイズ感の決定」、および複数の部品をガタつきなく強固に結合するための「組み付け構造の設計」において、何度もプロトタイピングと修正を繰り返して完成度を高めました。

【検証で得た学び / 次の課題】

今回の開発を通して、以下の技術的な改善点を見出し、次期モデルへのアップデート目標としています。

1. 逆運動学（Inverse Kinematics）の実装による拡張性の確保

現在は関節角度を直接指定する方式で、仕分け先が増えると動作パターンの追加が必要です。次は目標位置から関節角度を求める逆運動学を検討し、可動範囲や干渉を確認したうえで適用します。仕分け先の変更に対応しやすい構成を目指します。

2. 電源とノイズを測定して切り分ける

サーボの駆動・停止時に予期しない動作が生じました。電源変動やノイズは原因候補ですが、波形測定なしに逆起電力と断定しないことが課題です。次の試作では電源・接地・配線を確認し、必要な保護と電源分離を検討して、負荷を変えた試験で効果を確かめます。

3. エンドエフェクタ（ハンド部）の機構設計とギア精度の向上

アーム先端で荷物を掴むハンド部分の機構設計において、動力を伝達するギアの調整に反省点が残りました。CAD上での設計公差や、実際のギアの噛み合い（バックラッシュ）の調整が甘かったため、モーターのトルクが適切に伝達されず、対象物をうまく把持（グリップ）できないケースが発生しました。この物理的なハードウェア特有の課題を踏まえ、今後の設計ではギアのモジュールや軸間距離をより厳密に計算し、3Dプリンター等の出力精度も加味した上で、確実で安定した把持ができるエンドエフェクタ機構へとアップデートを図ります。

【システム概要】

カメラ画像から走行指令を推定するCNNと、車両の追従制御を組み合わせる自動運転ミニカーの開発です。ROS 2・Gazebo・PyTorchを使い、学習データの偏り、物理モデルの誤差、急加速時の不安定さを調べています。ここで紹介する走行改善はシミュレーションでの開発記録です。実機への移植と繰り返し走行の検証は今後の課題です。

【使用技術、ツール】

  • ロボット制御ミドルウェア： ROS 2 (Jazzy Jalisco)
  • シミュレーション環境： Gazebo Sim (Version 8.x), Antigravity CLI
  • AI / ディープラーニング： PyTorch (with CUDA), OpenCV
  • ハードウェア開発： Arduino IDE, KiCAD（予定）
  • 使用部品： Raspberry Pi 5, ODK-Dカメラ, サーボモーター, DCモーター, モータードライバー, XHコネクタ, ユニバーサル基板

【ハードウェア設計における課題と工夫】

実機試作に向けた初期ハードウェア開発において、以下の課題に直面し、それぞれ対策を講じました。

電源系統の設計ミスと回路修正

課題： ユニバーサル基板の初期設計段階で、モータードライバー用の電源ラインが不足している設計ミスを発見。
工夫： 回路図・実装図の段階でミスを検知し、コネクタを1つ追加することで対応。今後はこの経験をもとに、より可視化・検証がしやすいKiCADを用いた回路設計へと移行します。

確実な配線実装と接続信頼性の向上

課題： 振動の多いミニカーにおいて、配線の接触不良は致命的なトラブルの原因となる。また、スズメッキ線を用いた手作業でのハンダ付けは熱伝導の制御が難しく、イモハンダのリスクがあった。
工夫： すべての配線にXHコネクタを採用し、専用工具で端子を圧着することで物理的な接続信頼性を確保。ハンダ付けにおいては「予備ハンダの徹底」と「スズメッキ線をしっかり熱して熱効率を上げる」ことを意識し、堅牢な基板へと仕上げました。

今後の機体レイアウト最適化

課題： 走行時の安定性やメンテナンス性を考慮する必要がある。
工夫： ラズパイ5やカメラ、シャーシの配置をCAD上でモデル化（または既存モデルの選定）し、重量バランス（重心）を意識したパーツ配置と、整備しやすい配線レイアウトを設計中です。

【検証で得た学び / 次の課題】

学習だけでは安定走行に届かなかった経験から、データ、物理モデル、制御を分けて見直しました。以下は過去のシミュレーションでの改善過程です。ゲインや速度上限は当時の条件に依存し、実機へそのまま適用する値ではありません。

1. データ不均衡によるローカルミニマム（その場旋回ループ）の解消

反省点： 初期モデルで、その場を旋回し続ける挙動が発生しました。収集データに含まれる停止・旋回場面の偏りを原因候補として調べ、データの構成と走行結果を対応付けて見直しました。
Next Action： 停止状態での旋回や完全停止のデータを除く処理を加えて再学習しました。開発記録では低速での1周を確認しています。次は別の初期位置・条件でも評価し、改善が特定の走行条件だけに依存しないかを確認します。

2. システム同定（SysID）に基づくPID制御の導入とパラメータ適合

反省点： AIの出力のみ（End-to-End単体）では、速度を上げた際にカーブが不安定になり、完璧な学習データを用意し続けることの限界に直面しました。そこでAIには「目標値（目標速度・目標角度）」だけを出力させ、実際のタイヤ制御はPIDで行うハイブリッド方式を試みましたが、導入初期は車体がその場旋回するか壁に衝突する状態になりました。原因を追究したところ、機体の総質量（6.14kg）をはじめとするURDF（物理モデルパラメータ）に大きな誤差があり、ゲイン計算の前提が崩れていたことが判明しました。
Next Action： 車体重量の誤差を修正し、システム同定から得られた物理特性（無駄時間 $L=0.1$秒、時定数 $T=0.33$秒）をベースに、ジグラー・ニコルス法等を用いて以下の通りゲインを再計算・適合させました。 ・比例ゲイン ($K_p$): 3.92
・積分ゲイン ($K_i$): 0.65 （制御周期 30Hz換算）
・微分ゲイン ($K_d$): 6.0 （制御周期 30Hz換算） これにより、制御が破綻することなく高速化の土台を作ることができました。

3. 急激な車速変化に伴う慣性への対処（ローパスフィルターと減速ロジック）

反省点： PID制御とURDFの加速度制限の上限を3倍に引き上げたことで、直線での最高速度は大幅に向上したものの、1つ目のカーブを抜けた直後にステアリングに大きな数値が残ったまま車速が 3.0 m/s へ急上昇し、慣性によって制御不能（オーバーステア）となり壁に衝突する問題が発生しました。
Next Action： 急激なステアリング変化を滑らかにするため、操作量にローパスフィルターを導入しました。あわせて、カーブ進入時に自動で減速するシステムを組み込みました。さらに、従来のステアリング式「(0.4 × 前回の値) + (0.6 × AIの予測)」の配分を見直し、AIの予測の重みを 0.85 まで引き上げることで、ラインから外れそうになった際のリカバー力を高め、壁に激突せず1周できるよう改善しました。

4. 高速周回時の膨らみ抑制と振動（ハンチング）の防止

反省点： さらなる高速化を目指し、「未来予測の先行入力（車速に応じて早めにハンドルを切る）」を導入したところ、逆にカーブ前の段階でイン側に膨らみすぎて挙動が不安定化し、外側の壁に張り付くような走行ラインになってしまいました。また、実機を見据えた際、サーボモーターの突っ張り（過剰な応答）によるメカの破損リスクが懸念されました。
Next Action： 逆効果となっていた未来予測の先行入力を一度削除し、定常位置を真ん中に維持するため、固有角周波数 ω_n = 5.0、減衰比 ζ = 1.0 に再調整した以下のステップ応答ゲインへ上書きしました。 ・K_p_steer = 25.0 / K_d_steer = 10.0
・直線部最高速度上限: 3.5 m/s

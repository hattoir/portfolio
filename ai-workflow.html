DEVELOPMENT PROCESS

AIとつくる。
根拠で確かめる。

AIを、調べる・実装する・試す作業の相手として使っています。目的と完了条件を先に決め、結果を確認してから次へ進むことを大切にしています。

開発の一周を、記録に残す。

  1. 構想・要求整理何を実現したいか、制約と完了条件を自分で整理する。
  2. 調査・設計資料と既存コードを確認し、選択肢と未確認事項を残す。
  3. 作業分担・実装AIへ対象・許可範囲・成果物・試験条件を渡す。
  4. テスト・シミュレーション正常系だけでなく、誤入力、取消、未接続も試す。
  5. 結果の検証・人の判断差分と証拠を照合。公開・課金・実機操作はHuman Gateへ。
  6. Knowledge Vaultへ記録採用した判断、理由、結果を残し、次の調査・設計で再利用する。

開発上の進め方を整理した図です。全工程が自動化・本番統合済みという意味ではありません。

ツール名より、何を任せたか。

ChatGPT
構想・要求の言語化、資料をもとにした計画とレビュー。AI Labの設計文書では計画側の役割として整理しています。
Codex / Claude Code
コード調査、実装、テスト、変更内容のレビューを分担する開発支援。今回のポートフォリオ改修もCodexによる調査・実装を含みます。
OpenDots / Ollama
常駐ハブ側のエージェント実行・ローカル推論を担う基盤として開発・検証。模擬実行と実モデルの実行を分けて記録します。
Gemini / NotebookLM / Spark
Geminiは、さまざまなテーマについて詳しく調べるときに使っています。NotebookLMは論文やデータシートを読み解くために、Sparkはメールの管理に使っています。

長い作業を、曖昧な「完了」にしない。

途中の状態を残す

作業を依存関係ごとに分け、実行ID、対象版、成果物、失敗理由、次の作業を記録する設計です。タスクの記録とエージェントの現在の稼働は分けて表示します。

判断までの道筋を残す

Atlasでは、知識・タスク・実験・結果・判断をたどる画面を実装しています。ライブ接続を確認できないものを、動いているように表示しません。

開発の中で、どう使っているか。

JARVIS：音声の「成功」を分けて確かめる

目的・人の判断
声で伝えた意図と実際の操作が一致することを目指し、適用範囲や採用条件を人が決めます。本人の声での受入と、本番への適用判断は残っています。
AIに分担する作業
実装・テスト追加・ログ整理を支援。開発報告では、音声認識のヒントと意図判定を別々に比較しました。各試験を本人が手動実施したという意味ではありません。
問題と検証
合成音声を使った回復試験では5ターン中2ターンで誤認識。後の隔離比較では、同一の合成音声6件に対して新設定の意図一致は6/6、厳密な文字一致は2/6でした。文字起こし・意図・状態を別々に確かめています。

Serpens：設計とシミュレーションを行き来する

自分が考えること
蛇らしい動き、機構、可動域、ハードウェアの条件。CAD上の形状と干渉を確認し、比較する設計案を考えます。
AIと分担すること
調査、コード作成、シミュレーション、案の比較。MuJoCoはAI支援で導入を進めている段階で、自分だけで使いこなせる技術とは区別しています。
判断に残すこと
モデルの版と条件を添えて結果を確認します。CADの可動域や模擬動作だけで、実機のトルク・耐久性・安全性を確かめたことにはしません。実機と基板の製作・検証はこれからです。

AIの提案と、操作の許可を分ける。

実行前に対象、権限、期限、計画の内容を照合し、変更された計画や範囲外の操作を拒否する仕組みを検証しています。未知の操作は実行へ昇格させず、履歴を残します。

外部公開・課金・危険な実機動作は、人が内容と影響を確認して承認します。承認待ちを成功と扱わず、AIによる実装も安全性が確認済みとは限らない前提で進めます。
